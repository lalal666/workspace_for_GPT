# 澜潮负荷端智能硬件 PRD

澜潮科技布局源、网、荷、储全链路。本技能面向「荷」侧的能源管控节点。从终端参与的业务闭环定义产品，按需串起感知、通信、决策、执行与反馈。云端、微信小程序、终端硬件和固件构成同一解决方案。父节点、网关、其他系统以及本地和云端各自承担的职责以项目基线为准。

## 取材与提问

1. 先看本项目的现行 PRD、MRD、评审决议、SKU 定义、网络和物模型资料。按需核对研发目标、测试报告和 BOM，记录来源版本、适用产品和确认状态。用户本轮的明确决策可以更新对应基线，并记录影响。资料冲突时列出原值、出处和待拍板事项，结合适用范围与评审状态判断，勿仅按文件日期选取。
2. 标注「已确认」「建议方案」「待确认」。对来自预研、估算和样机的数值，记录依据、工况和适用版本。BOM 用于核对样机或采购基线，产品承诺以确认的需求及适用测试证据为准。
3. 发现会改变产品边界、链路责任、安全行为、对外承诺或验收口径的缺口时，集中向用户问少量具体问题，说明选项和影响。先完成资料足以支持的部分。为其余缺口记录拟确认角色、所需证据及受影响的评审或交付阶段。未知的型号、数值、协议、标准、负责人和状态保留待确认。

## 编写、修订与评审

1. **从场景定范围。** 写明本期阶段、问题及来源、使用和运维角色、目标与成功指标。用代表性场景讲清谁在什么条件下，希望哪类负荷发生什么变化。定义本期 SKU、共用能力、SKU 差异、涉及的端及外部依赖。若声称节能，明确计量来源、比较基线、统计周期、现场条件和舒适性或业务约束，分别记录预计效果和实测效果。
2. **把一次业务闭环讲完整。** 追踪触发或采样、数据送达、策略执行位置、控制仲裁、设备动作及可用反馈、用户看到的结果。对变更涉及的链路写明正常、失效和恢复行为。跨端控制、物模型、入网、离线和升级按 [跨端协作与设备生命周期](references/system-behavior.md) 展开。每条需求分配稳定 ID，标明适用 SKU、涉及端、牵头角色、优先级与验收条目。采用项目既有编号和职责约定。
3. **把硬件条件写进需求。** 根据 [品类与硬件验证](references/hardware-verification.md) 选择与场景和阶段有关的检查项。写清供电、安装、负载、环境、容量和性能指标的适用条件。遇到响应与功耗、检测与误报、舒适性与节能等取舍，给出待决选项和对应的验证方式。涉及安规、无线或认证时，按目标市场和具体 SKU 核查适用性、版本及证据。
4. **让验收能复现。** 对本期需求关联验收项或明确验收证据，并覆盖关键场景的边界与恢复。记录适用型号及版本、安装和供电条件、网络条件、负载或样本量、执行动作、端到端测量起止点、判定阈值和取证方式。指标尚无依据时，补齐测量设计，阈值挂到待决项。分别标记单端验证、系统联调和现场验收的完成状态。
5. **按研发分工交付。** 对齐项目已有 MRD 至 PRD 的来源关系，保留文档控制和评审记录。按需关联工业设计（ID）、结构（MD）、硬件（HW）、固件（FW）、云平台、微信小程序、测试（TE）、工艺（PE）及交付运维。明确共用的接口基线、跨团队依赖和阶段出口证据。需要拆解到 PDT 时，沿用项目确定的 BA/SE 或产品负责人安排。

- **新建**时优先沿用项目现有 PRD 模板。没有模板时用 [澜潮负荷端 PRD 模板](assets/prd-template.md)，按系统、SKU 或功能变更缩放范围。早期草稿可只展开影响决策和联调的章节。
- **修订**时从现行版本出发，保留有效内容和需求 ID。记录新增、修改、删除或澄清及依据，并检查受影响的 SKU、跨端接口、兼容矩阵、验收项和里程碑。用户要求另存评审版时从基线复制。
- **评审**时优先给出阻塞评审、联调或交付的缺口，标明章节或需求 ID、影响、应确认角色、补齐方式和所需证据。按资料判断能否进入目标阶段，引用已有结论或实测证据。用户要求修订时同步落到文档。

## 交付前检查

- 每个本期关键场景能追到对应的 SKU、职责端、需求和验收证据。涉及控制时，查看状态的角色能知道动作执行到哪一步、依据是什么以及何时更新。
- 共用项只维护一份有效基线，SKU 差异和版本例外能从对应需求直接定位。离线、掉电、低功耗或升级中的失效路径有适用的恢复判定。
- 硬件与系统指标有工况和测量口径，待确认项有证据要求。规格、评审、测试和发布状态以实际记录为准。
- 遵循当前项目的格式和目录约定。在「多合一」中，将中间缓存、摘录和验证稿放入 `middle`，将阶段性交付物放入 `out`。按用户指定的路径处理现有主文档和附件。
