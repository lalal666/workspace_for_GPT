#### 一、产品概述与双形态定位

一句话定义：撕开背胶一贴即用、不接线不换电、坐在工位不动也不会关灯的存在传感器；完全无光的位置插一根 USB 就能获得更强性能。

#### 1.1 背景与要解决的问题

| 现有方案 | 致命缺陷 | 现场表现 | 

| 纯 PIR 人体感应 | 只对移动热源响应，静止即判无人 | 办公位静坐 5 分钟灯就灭；被迫把延时调到 20–30 min，节能率回落到 30% 以下 | 

| 纯 24G 雷达 | 对金属摆动、管道、穿墙敏感；常驻工作耗电高 | 卷帘门、管道、窗帘导致"无人常亮"；电池型产品几个月没电 | 

| 市电/电池型存在传感器 | 需布线或 1–2 年换电池 | 改造布线成本高于设备本身；万级点位无法规模化运维 | 

本产品解法：PIR 做门控与主发现通道，雷达只在 PIR 静默后才启动做"静止保持"确认；能量管理 IC 统一管理光伏 / 超容 / 电池三源；3M 胶贴与镭雕扫码解决施工速度；USB 作为第二形态覆盖完全无光场景。

#### 1.2 双形态定位

| 形态 | 供能方式 | 适用场景 | 能力差异 | 

| 形态 A
微能量 | 光伏 + 50F 超容 + 400 mAh 电池兜底，三源由能量管理 IC 统一管理 | 办公、走廊、卫生间、会议室、靠窗区域——常态照度 ≥30 lux | 标准性能：雷达延迟确认 60 s 起步，能量不足可延长；受 5 级能量策略约束 | 

| 形态 B
USB 外供 | USB 5 V 直供超容与升降压芯片，超容保持满电，电池不消耗 | 地库深处、密闭机房、设备间、无窗库房——照度长期 <10 lux | 外供电高性能模式：雷达延迟可缩至 15–30 s、灵敏度可上调、无低电降级、全量上报 | 

#### 1.3 产品边界

#### 本产品做（In Scope）

- PIR 门控 + 24G 延迟确认的双鉴存在检测

- 微能量与 USB 双供能，自动识别切换

- 光照四用途：联动 / 安装质检 / 免开灯 / 灯具故障辅助判断

- 56 条事件的全量定义与上报策略配置

- 2.4G 纯叶子终端，经 L2 CCO → L1 CCO 上联

- 3M 胶贴随手贴；镭雕设备码 + App 位置录入

- 硬件单刀开关（运输模式 + 手动复位）

- 无孔化外观

#### 本产品不做（Out of Scope）

- 不做摄像头、音频采集、身份识别

- 雷达不做独立触发源，只在 PIR 之后启动

- 不做低频保底扫描（已按方案 1 定案）

- 不做中继/路由；不做 Sub-G、不做 PLC

- 不做独立网关

- 不做距离分档 / 多人计数（转预留）

- 不做室外、雨淋；不做粗糙易脱落墙面

#### 3.2 供能路径拆解

三条路径的角色必须分清，否则会误判"开关断开后设备应该完全不工作"。

| 路径 | 走向 | 关键特性 | 

| 主能量路径 | 光伏 / 超容 / 电池 → 能量管理 IC（三源统一管理）→ SW1 单刀开关 → Buck-Boost → 系统 | 三源由一个 IC 统一调度，输出单路；开关就切在这一路上 | 

| USB 充电路径 | USB → 锂超容（直充，不经 IC） | 现场补电与产线预充走这条，速度快、不受 IC 充电逻辑限制 | 

| USB 直供路径 | USB → Buck-Boost → 系统（绕过 SW1） | 运输模式（开关 OFF）下插 USB 设备仍能工作——产线可在已拨 OFF 状态完成身份写入与测试 | 

    USB 旁路这个设计很实用。如果 USB 也要经过开关，产线就得"拨 ON 写入 → 拨 OFF 包装"，多一道动作且容易漏拨。现在可以在"已进入运输模式"的状态下直接插 USB 完成写入、校验、测试，最后拔线包装——漏拨风险大幅降低。

#### 3.3 两种供能形态的行为差异

| 项目 | 形态 A 微能量 | 形态 B USB 外供 | 

| 雷达延迟确认
T_radar_delay | 60 s 起步（能量不足延长至 120 / 300 s） | 可缩至 15–30 s | 

| 雷达单次扫描 | T_scan ≤5 s，典型 2 s（由模组实测标定写入固件，两形态相同） | 

| 雷达占空比 | 2 s ÷ 60 s ≈ 3.3%（且 PIR 活跃时长为 0） | 2 s ÷ 15 s ≈ 13% | 

| 微动灵敏度 | 默认档 | 可上调 1 档 | 

| 事件上报 | 受 5 级能量策略约束，P2 可能被压缩 | 全量上报，不受限 | 

| 电池寿命顾虑 | 存在（视照度） | 无，电池完全不消耗 | 

| 充电中行为 | — | 边充边检，检测不中断 | 

| 识别与切换 | 自动识别 USB 插入/拔出，≤5 s 切换供能模式并上报 powerSource；切换过程检测不中断、不重启 | 

    边充边检不影响充电速度。USB 输入能力（5 V／≥500 mA，限流上限 300 mA）比检测负载高出三个数量级——检测工作电流是几十 µA 量级，占比不足 1%，可以忽略。因此充电期间检测照常运行，雷达延迟确认参数不做任何临时调整，超容 2.5→3.5 V 仍 <10 min 完成。

    唯一需要保留的保护是限流 ≤300 mA（防 USB 源过流）与防反灌；安装人员插线后会看到指示灯充电状态，检测功能同时在跑，属正常。

#### 3.4 覆盖角：触发角 120° 与保持角 150°

两个角度不是"重叠与不重叠"的关系，而是两种不同的职责：PIR 负责"发现人"（触发），雷达负责"记住人还在"（保持）。

| 区域（以安装点垂线为 0°） | PIR 触发角
（全角 120°） | 雷达保持角
（全角 150°） | 实际能力 | 

| 0°–60°（核心区） | 可触发 | 可保持 | 完整双鉴：能发现人，也能维持"有人" | 

| 60°–75°（外环区） | 不可触发 | 可保持 | 只能保持：若人先在内圈被发现、再走到外环，雷达能继续维持；若人只在外环且不动，永远不会被发现 | 

| >75° | 不可触发 | 不可保持 | 无能力 | 

    这样理解就顺了：

    · PIR 120° = 有效触发角，它决定了"这个点位能发现多大范围的人"，是产品的对外承诺值；

    · 雷达 150° = 有效保持角，它决定了"人被发现后能在多大范围内继续被维持"，是体验增强值；

    · 外环 60°–75° 的价值在于：人从内圈走过、转身到侧后方时，灯不会因为"走出 PIR 视野"而误灭——这是雷达宽角带来的实际收益；

    · 局限同样要讲清：如果有人在侧后方一直静止不动，PIR 从未触发，系统就不会知道他在。这不是缺陷，是 PIR 门控架构的必然取舍。

对外表述规范：规格书写"有效探测角 120°（触发）／维持角 150°（保持）"，不写"探测角 150°"。销售布点时按 120° 计算覆盖，外环作为容错余量而非设计余量。

#### 3.5 外观设计要求：无孔化与隐私观感

| # | 设计要求 | 具体做法 | 要避免的观感 |

| 机制 | 要求 | 说明 |

#### 4.3 三条硬约束

| # | 约束 | 原因与影响 | 

| 1 | 不可作为中继 / 路由节点 | 中继需 7×24 常收，功耗 mA 级。误编为父节点会陷入"能量耗尽—重启—再被选为父"死循环。入网须带 devClass=HARVEST_LEAF、canRelay=false | 

| 2 | 仅 2.4G，不接 PLC、不用 Sub-G | 无市电耦合无法做 PLC；统一 2.4G 单模 | 

| 3 | 父节点必须缓存 OTA 包 | 节点长期休眠无法维持长连接下载；资源不足走小分片+唤醒逐片下发 | 

#### 4.4 双向暂存与失败回退

| 方向 | 机制 | 溢出处理 | 节点侧配合 | 

| 下行 | 父节点为休眠子节点暂存下行报文，唤醒窗口内投递 | 溢出则上游返回失败，云侧重试 | 窗口内未收到即继续休眠 | 

| 本地广播 | 不经树形路径：2.4G 泛洪组播直达同群组灯节点，TTL ≤4 | 超 TTL 自然丢弃；无确认则重播 2 次，仍无确认报 E606 | 灯侧按 evtSeq 去重后执行，并回短 ACK | 

| 上行 | 父节点接收后暂存再转发，防父节点离线丢报文 | 超暂存深度则通知发送失败，节点写入事件缓存，下次唤醒重传 | "未确认→本地缓存→重传"；缓存满时上报丢弃条数 | 

上行暂存比下行更重要：下行可重发，上行丢失是事件永久丢失。建议"父节点 ACK 后才删本地缓存"的两阶段语义。

#### 七、事件定义与上报配置体系

本章是全文档的核心依据：54 条事件逐条给出定义（触发条件 + 含义），并把事件出口拆成三条独立通道——本地广播、父节点上行、云端上报——分别规定默认方式、周期与可禁用性。研发可直接按此实现，测试可直接按此验收。

#### 7.1 六条设计原则

- 每条事件必须有可判定的触发条件。"有人离开"不是一个名字，而是一组明确条件：离开判决计数达标 + 连续 N_leave 次雷达判无目标。没有触发条件的事件等于没有定义。

- 三条出口必须分开定义，不能用一个"上报方式"字段笼统表达。"要多快送到灯"和"要多省送到云"是两个正交需求。用同一个字段同时表达，结果只能二选一——要么为了开灯快而全部即时上云（耗电），要么为了省电而让开灯变慢（体验崩）。拆成三条后，两者可以同时最优。

- 上报方式是设备行为，必须是有限枚举。设备是休眠终端，无法响应任意节奏。所有配置必须落在设备能执行的有限档位内。

- 三级硬约束不可被配置突破。① 能量底线 ② 安全合规类（防拆、滞留、双鉴失效必须即时且不可禁用）③ 数据完整性（缓存溢出、白名单失败、联动确认超时必须报）。

- 本地配置是受控变更，必须经云端人工确认。生效后进入"待确认"态，授权人员确认才固化基线；72 h 未确认告警，7 天自动回退。

- 聚合不是丢弃，是延迟。聚合类事件仍完整记录在本地缓存，周期到达打包上报；期间若发生更高优先级事件，打包一并提前发送。

#### 7.2 三通道出口模型

一条事件从设备发出，可能走三条完全不同的路。三者的目的、时延、确认语义、失败处理都不一样，必须分别配置、分别监控。

| 通道 | 标识 | 目的 | 典型时延 | 确认语义 | 失败处理 | 

| D1 本地广播 | LB | 立即让灯/执行器动作，不等网络、不等云 | ≤300 ms（泛洪，≤4 跳） | 灯侧 ACK 经父节点回传，代表"指令已被灯收到" | 重播 2 次（间隔随机 20–50 ms 防碰撞）；3 次无确认 → 上报 E606 | 

| D2 父节点上行 | UL | 把事件交进网络，保证不丢 | 1 个唤醒窗口内（100–500 ms 命中，最长 ≤5 min） | 父节点 ACK，代表"事件已进入父节点暂存队列" | 未 ACK 则本地保留、下次唤醒重传；父节点暂存溢出须回通知（见 4.4） | 

| D3 云端上报 | CL | 可运营、可统计、可追溯 | I ≤1 s／A 15 min–24 h／H 300–1800 s／L 不上报 | 父节点 ACK 即视为"设备侧完成投递" | 按 A 档缓存、补报；缓存溢出报 E508 |

    典型组合：有人进入 = D1 即时广播（灯 300 ms 亮，要求灯侧确认）+ D2 父节点 ACK（事件不丢）+ D3 云端聚合 15 min（省钱省空口）。三条并行，互不等待。

    最容易埋的误解：父节点 ACK ≠ 云端已收到。ACK 只证明事件进了父节点暂存队列，而父节点到 CCO 是多跳，暂存溢出还会丢。若把两者混为一谈，会出现"设备以为上报成功、云端一条没收到"的静默丢数据——而且设备侧日志完全正常，排查会耗掉大量时间。

    处置：每条事件带递增 evtSeq；云端按设备维度做序号连续性校验，发现空号即判丢事件并下发补报请求。这一条应写进通信协议，属于必做项而非优化项。

#### 7.3 本地广播与灯侧确认

为什么本地必须单独占一条通道：云端往返最短也是一个唤醒窗口（秒级），而开灯要求 ≤300 ms 用户可感知。两者差一个数量级，不可能用同一条路满足。

| 要素 | 设计 | 

| 承载方式 | 2.4G 泛洪组播，TTL ≤4 跳；携带群组 ID（32 个 group-ID 槽位）、动作码、evtSeq、需确认标志 | 

| 时延预算 | 组帧 ≤30 ms + 空口 ≤15 ms/跳 + 灯侧处理 ≤50 ms → 典型单跳 ≤120 ms，4 跳 ≤300 ms | 

| 确认机制 | 灯侧回短 ACK 帧（不含业务载荷），由父节点汇聚后回传给本设备（这正是"由父节点确认灯是否收到"的落地方式）；超时 T_ack 默认 200 ms | 

| 重播策略 | 超时未确认 → 重播，最多 2 次，间隔随机 20–50 ms（打散碰撞）；3 次仍无确认 → 上报 E606 | 

| 去重 | 灯侧按 evtSeq 去重，避免重播导致重复动作或重复计时 | 

| 空口代价 | 单次约 35 ms 占空（发 15 ms + 收窗 20 ms）。按 60 次/日计，占用可忽略；但密集部署仍须限制 TTL 与群组规模（≤8 台/父节点） | 

    E606 与 E605 的分工要说清，否则现场会误判：

    · E606 联动确认超时：灯没回 ACK → 指令没送到、或灯离线、或群组 ID 配错 → 查通信。

    · E605 照明回路疑似故障：灯回了 ACK 但照度没升 → 指令到了、灯没亮 → 查灯具/驱动。

    两者同时出现时优先查通信——因为通信不通时 E605 的判定本身也不可信。这个判断逻辑放在云端做，设备端不做。

#### 7.4 云端上报四档

云端上报（D3）的节奏只有四档，但每一档的周期、条数、重传都可配，不写死在固件里。

| 标识 | 方式 | 时延 | 设备行为 | 适用 | 

| I | 即时 Immediate | ≤1 s（P1）
≤300 ms（P0 场景） | 事件发生立即组帧发出，按配置重传 0–2 次，不等唤醒窗口 | 安全类、故障类、必须实时可见的主事件 | 

| A | 聚合 Aggregate | 周期 15 min / 30 min / 1 h / 2 h / 6 h / 12 h / 24 h 七档任选 | 写入环形缓存，到期打包上报；超条数上限则拆包或按优先级保留 | 统计类、诊断类、业务主事件（靠本地广播保证即时） | 

| H | 随心跳 Heartbeat | 跟随心跳周期 300–1800 s 可配 | 不单独发帧，挂在下次心跳帧中捎带，最省电 | 低频状态类 | 

| L | 仅本地 Local | 不主动上报 | 只记本地缓存，可由 readDiagSnapshot 读出 | 调试类、高频低价值类 | 

    "有人进入"配 A 档会不会导致云端看着延迟？不会。因为开灯由 D1 本地广播完成，与 D3 无关。云端配 15 min 聚合只影响"报表里这条记录晚 15 分钟出现"，不影响现场任何一秒钟的体验。

    这正是三通道拆分的价值：把"实时"归本地、"可运营"归云端。安防场景若确实需要云端实时告警，把 E101/E105 改回 I 档即可，代价是每个点位日均多耗约 10–20 µAh。

#### 7.7 配置通道：云端下发 与 本地蓝牙

| 维度 | 云端下发（主通道） | 本地手机蓝牙（辅助通道） | 

| 路径 | 云 → 网关 → L1 CCO → L2 CCO → 父节点暂存 → 唤醒窗口投递 | 手机 App → BLE 直连设备 | 

| 前置条件 | 设备在线、父节点有暂存余量 | 需先触发维护模式（长按按键 3 s 或扫码唤醒），进入长唤醒窗口 | 

| 生效时延 | 1 个唤醒周期内（默认 ≤5 min） | 即时（≤3 s） | 

| 确认机制 | 直接生效并经回执确认，即为基线 | 生效后进入"待确认"态并上报云端，由人工确认后固化基线；三态：待确认 / 已确认 / 已回退 | 

| 有效期 | 长期有效 | 待确认期上限：72 h 告警升级，7 天未确认自动回退基线 | 

| 适用场景 | 批量配置、按群组/项目统一策略、远程运维 | 现场调试、离线点位、单点异常排查、安装期快速验证 | 

| 权限 | 项目管理员及以上；留操作日志 | 现场技术人员；需输入设备鉴权码 | 

    为什么必须有本地蓝牙通道：①离线点位——网络未覆盖或父节点故障时云端下不到；②安装期调参——装完想立刻验证灵敏度，等云端往返太慢；③误报排查——临时把某点位切成"仅本地记录"观察，不影响整层策略。

    但必须是"受控变更"而非"永久改写"，否则现场调完就忘，云端看到的策略与设备实际行为不一致——这是运维事故的经典来源。

#### 7.8 配置优先级与冲突仲裁

    ① 能量底线（最高，不可被任何配置突破）
    低电强制压缩：L3 起 P2 转 H；L4 起 P2 停发、仅 P0/P1；L5 仅 P0。此时配置的"A 档 15 min"会被改写为实际执行档，并回执告知。

    ② 安全与完整性硬约束（不可关闭）
    24 条不可禁用事件（防拆、滞留、双鉴失效、PIR 自检失败、超容欠压、电池耗尽、缓存溢出、白名单失败、联动确认超时等）强制 I 档，重传 ≥1 次。

    ③ 云端基线配置（长期有效）
    按项目 / 楼栋 / 楼层 / 群组 / 单点五级下发，粒度最细覆盖最粗；支持模板化批量应用。

    ④ 本地蓝牙配置（需云端人工确认才固化；7 天未确认自动回退）
    现场调试用；生效后进入"待确认"，不可突破①②；超时回退前 24 h 提前通知。

    最容易出的运维事故：低电时配置"看着生效、实际被强制改写"。举例：云端把 E102 配成"聚合 15 min"，但设备在 L4 档 P2 已停发。若设备不回执实际执行档，运维会以为"配了 15 min 为什么没数据"。

    因此每次下发必须在回执中同时返回"配置值"与"当前实际执行值"，不一致时置告警标记。这条要写进 setReportPolicy 出参定义。

#### 7.11 上报能耗与配额

两个口径分开算：本地广播是动作帧（短、频次随人流量），云端上报是数据帧（长、频次随策略）。

| 单次动作 | 能耗构成 | 单次能耗 | 说明 | 

| 本地广播一次（含灯侧确认收窗） | 发 15 ms + 收窗 20 ms × 5 mA | 约 0.05 µAh | 最快的一类，几乎可忽略 | 

| 父节点 ACK 等待窗 | 额外 50 ms 接收 × 5 mA | 约 0.07 µAh | 仅"必须 ACK"的事件产生 | 

| 云端即时上报一次 | 200 ms × 5 mA（含唤醒/组帧/发射） | 约 0.28 µAh | 即时档的主成本 | 

| 聚合打包（一包含 8 条） | 约 260 ms × 5 mA | 约 0.36 µAh／包
（折合 0.045 µAh／条） | 聚合省电的本质就在这里 | 

| 配置组合 | 日均本地广播 | 日均云端上报 | 合计能耗/日 | 占整机预算 | 

| T1 办公标准 | 约 60 次 | 约 40 次 | 约 14 µAh | 约 6% 占比很低 | 

| T3 走廊节能 | 约 20 次 | 约 12 次 | 约 4 µAh | 约 3% | 

| T5 极限省电 | 约 8 次 | 约 6 次 | <2 µAh | <1% | 

| T6 诊断排查 | 约 60 次 | 约 300–800 次 | 约 87–227 µAh | 36–95% 占比显著升高 | 

    结论：真正吃电的不是上报，而是 PIR 常开与雷达扫描。按日均预算约 240 µAh 计：

    · PIR 常开约 120 µAh（占 50%）　· 雷达扫描约 60 µAh（占 25%）　· MCU 与射频约 40 µAh　· 漏电与静态约 20 µAh。

    所以省电的第一优先级永远是减少雷达扫描次数（拉长 T_radar_delay、PIR 活跃时重置计时器），而不是压缩上报。T6 诊断模板仍建议限期使用（7 天），但理由不是"击穿预算"，而是"长期高占用会吃掉能量余量，导致低电降级把关键事件也压掉"。

#### 八、性能指标与验收方法（含定义）

每个指标都给出"定义 / 测试口径"，避免研发与测试对同一名词理解不一致。未标注测试条件的指标不可用于对外宣传。

| 指标 | 定义 / 测试口径 | 目标值 | 测试条件 | 验收方法 | 

| 移动检出率 | 目标在标准路径上径向穿越探测区 N 次，设备成功上报"有人进入"（E101）的次数占比 | >99% | 3 m 高，25 ℃，0.5–1.5 m/s 径向，N=100 | 漏检 ≤1 次；每次穿越间隔 ≥30 s 确保回到无人态 |

#### 九、能量预算与续航模型

因雷达改为"延迟确认 + PIR 重置"机制，雷达占空从 13% 降至约 3.3%，且 PIR 活跃时完全为 0。整机功耗与平衡照度全面下修。

#### 9.1 三态功耗模型

| 耗能项 | 无人态 | 有人·活跃 | 有人·静止 | 说明 | 

| PIR 通道（常开） | 2–5 µA | 2–5 µA | 2–5 µA | 唯一 7×24 工作的传感器，也是最大单项耗电 | 

| 24G 雷达 | 0 | 0（计时器不断重置） | 约 5 µA | 占空 2 s÷60 s≈3.3%，扫描期均值 ≤150 µA | 

| MCU 休眠 | 1–3 µA | 1–3 µA | 1–3 µA | 深度休眠 | 

| 上报能耗（折算） | 0.3 µA | 0.8 µA | 0.8 µA | 按 0.28 µAh/次，日均 30–60 次 | 

| 超容漏电 | 2 µA | 2 µA | 2 µA | 器件固有 | 

| 能量管理 IC + DC-DC 静态 | 2.3 µA | 2.3 µA | 2.3 µA | IC 300 nA + DC-DC 约 2 µA | 

| 光照通道 | <0.5 µA | <0.5 µA | <0.5 µA | 间歇采样 | 

| 合计 | 约 8–11 µA | 约 9–12 µA | 约 14–17 µA | 目标：无人 ≤11、活跃 ≤12、静止 ≤17 | 

    延迟确认机制带来的最大收益：PIR 活跃时雷达完全不启动。人一直在动时，PIR 每次触发都把 60 s 计时器重置，雷达连上电的机会都没有——此时整机功耗与无人态几乎相同（约 9–12 µA）。只有人坐下不动、PIR 静默满 60 s，雷达才出马确认一次。

    这个设计同时满足了两个看似矛盾的目标：有人时省电，且静止时不误判无人。

#### 9.2 日均消耗与能量平衡

| 场景 | 使用剖面 | 日均消耗 | 平衡所需照度 | 结论 | 

| 开放办公 | 有人 12 h（半静止） | 约 288 µAh（≈12 µA） | 约 48 lux（10 h 采集） | 50 lux 可自持 电池零消耗 | 

| 会议室 | 有人 6 h | 约 190 µAh（≈8 µA） | 约 32 lux | 低照度可自持 | 

| 走廊（含白天降频） | 累计 3 h 有人 | 约 110 µAh（≈4.6 µA） | 约 18 lux | 自持能力很强 | 

| 地库（形态 A 强上） | 有人 14 h | 约 330 µAh | 无光不可平衡 | 应改用形态 B | 

场景差异：办公场景日均约 12 µA，平衡照度约 48 lux。走廊场景从 23 lux 降至约 18 lux。

#### 9.3 超容可用能量与续航

| 项目 | 计算 | 结论 | 

| 可用能量（3.5→2.5 V） | ½ × 50 × (3.5²−2.5²) = 150 J | 出厂预充 3.5 V，保护下限 2.5 V | 

| 无光续航（仅超容，无人态） | 137 J ÷ (10 µA×3.3 V×86400) ≈ 48 天 | 缓冲充裕 | 

| 无光续航（仅超容，有人静止） | 137 J ÷ (16 µA×3.3 V×86400) ≈ 30 天 | 缓冲充裕 | 

| 电池切入后续航 | 400 mAh ÷ 288 µAh/日 ≈ 1388 天 | 按 50% DOD 约 1.9 年 | 

| USB 补电（边充边检） | 150 J 由 5 V 输入；检测负载几十 µA，占比 <1% | <10 min 达 3.5 V | 

运输模式（开关 OFF）：待机电流约 2.3 µA（超容 2 µA + IC 0.3 µA）。按 ΔV = I·t/C 计算，月降约 120 mV，6 个月降约 0.72 V（3.5 → 2.78 V），降到 2.5 V 保护点约需 8.4 个月。故：库存 ≤8 个月可直接安装；超 8 个月必须 USB 补电（<10 min）。

#### 9.4 五级能量策略（与延迟确认联动）

| 等级 | 超容电压 | T_radar_delay | 心跳/聚合 | 上报方式强制改写 | 发射功率 | 其他 | 

| L1 | ≥3.35 V | 30 s | 300 s / 15 min | 按配置执行 | 100% | 全功能 | 

| L2 | 3.2–3.35 V | 60 s（默认） | 300 s / 1 h | 按配置执行 | 100% | 默认档 | 

| L3 | 3.0–3.2 V | 120 s | 600 s / 6 h | P2 由 A 转 H | 75% | 积分时间加长 | 

| L4 | 2.7–3.0 V | 180 s | 900 s / 24 h | P2 停发；仅 P0/P1 | 50% | N_leave 加至 5 | 

| L5 | <2.7 V（电池已切入） | 300 s | 1800 s / 24 h | 仅 P0 | 25% | N_leave 加至 6 | 

    低电档的取舍：延迟拉长到 300 s 是"用精度换生存"，这个交换是对的。T_radar_delay 从 60 s 拉到 300 s，雷达鉴别次数随之降到 1/5，日均功耗可再降约 20–30 µAh；代价是静止维持分辨率下降到分钟级，因此 N_leave 必须同步加大（L4→5、L5→6），否则会出现"电量越低越容易误关灯"的反常体验。

    两个必须接受的边界：① 最坏判离时延可达 N_leave × T_radar_delay（L5 档 6×300 s = 30 min），灯可能白亮较久；② 这类点位应配"最大点亮时长"上限（灯具侧兜底，默认 30 min 强制关闭）避免长时间空亮。

| 部署场景 | 日均消耗 | 微能量贡献 | 电池预计寿命 | 

| 靠窗办公 | 约 288 µAh | 完全覆盖 | ≥5 年（存储寿命） |

#### 十、双鉴融合逻辑与雷达时序

三个时间参数必须分清：T_scan（单次扫描时长）、T_radar_delay（延迟确认时间）、W_verify（校验窗口）。保持阶段的雷达启动由 PIR 活动动态推迟，而非固定周期。

#### 10.1 三个时间参数

| 参数 | 符号 | 取值 | 定义与约束 | 

| 单次扫描时长 | T_scan | ≤5 s，典型 2 s | 雷达从上电到输出有效结果的时长，由模组实测标定写入固件（只读 tScan）。低温/远距会延长 | 

| 延迟确认时间 | T_radar_delay | 15/30/60/120/180/300 s | 有人态下，从"最后一次 PIR 触发"开始计时；到期才启动雷达扫描。PIR 每次触发即重置 | 

| 校验窗口 | W_verify | 默认 T_scan+1 s | 硬约束：W_verify ≥ T_scan。小于 T_scan 会导致雷达未出结果就判回滚 |

#### 10.5 三个残留风险的处置（不做保底扫描）

| # | 残余风险 | 表现 | 已收敛的缓解手段 | 

| 1 | PIR 失效 → 产品静默失效 | 镜片被贴、信号链开路时雷达永不启动，彻底失效且不自知 | ① PIR 自检提至 6 h ② "采集正常+通信正常+连续 7 天零触发"→E113 ③ 后台批量自检 ④ 安装期遮蔽即被发现（E408） | 

| 2 | 极限静止检出盲区 | 人被判无人后完全不动且 PIR 无触发，系统停在 S0、雷达关闭，无法重新发现 | ① N_leave 4–6 次 ② T_leave ≥3 min ③ 保持态 T_radar_delay ≤60 s ④ 布点冗余 ⑤ 规格书明示适用边界 | 

| 3 | 外环 60°–75° 不可触发 | 人只在该环带从静止开始，永远不会被发现 | ① 规格书标"触发角 120°" ② 布点按 120° 计算 ③ 外环作容错余量而非设计余量 | 

    请在投标与方案文档中主动写明：本产品不承诺"在完全无人活动的封闭空间中长期检测人的存在"，且外环 60°–75° 区域不能作为设计覆盖使用。此类场景（单独值班室、ICU 陪护、大进深侧向区域）应改用常供电 + 常开雷达方案。事前说明成本远低于事后解释。

#### 11.3 镭雕设备码与位置录入

#### 11.3.1 镭雕码内容与工艺

| 要素 | 要求 | 说明 | 

| 承载内容 | modelCode + MAC(12 位) + batch + mfgDate + hwVer | 一扫带出全部出厂信息，消除手输 MAC 的错录风险 | 

| 码制 | QR 或 DataMatrix（推荐后者：同面积信息密度更高、低对比度更易识读） | 需兼容手机摄像头与工业扫码枪 | 

| 尺寸与位置 | ≥8×8 mm；底面或侧面凹槽，避开探测窗与 USB 口 | 与开关、USB 口同区，用同色盖片遮蔽 | 

| 对比度 | PCS ≥0.3；深色壳用浅色打标，浅色壳用深色打标 | 深色壳对比度是最大风险，打样阶段必须实测 | 

| 耐磨耐污 | 酒精擦拭 50 次后仍可识读 | 设备装在高处，后期难清洁 | 

| 扫码成功率 | 一次 ≥99.5%；两次内 ≥99.9% | 列入来料与出货检验项 | 

#### 11.3.2 产线写入与三重一致性校验

| # | 工序 | 动作 | 合格判定 | 

| 1 | 镭雕 | 激光打标机在外壳底面刻码（型号+MAC+批次+日期+hwVer） | 可读、对比度达标 | 

| 2 | 扫码读码 | 产线扫码枪读取镭雕内容，自动录入产线系统 | 一次读取成功；失败则重刻或判废 | 

| 3 | 写入内部存储 | 经测试工装（USB，开关可保持 OFF）写入设备非易失存储专用区 | 写入成功回读校验值 | 

| 4 | 回读比对 | 从设备读回内部存储，与扫码结果逐字段比对 | 完全一致；不一致不得出厂 | 

| 5 | MAC 一致性 | 核对内部存储 MAC 与芯片实际广播 MAC | 一致；否则判为标错/改装 | 

| 6 | 预充与运输模式 | 超容预充至 3.5 V → 拨开关至 OFF → 包装 | 待机电流 ≤2.5 µA（抽检） | 

    三重一致性校验的价值：镭雕码（物理铭牌）、内部存储（产线写入）、实际 MAC（芯片固有）三者必须一致。任一层被篡改或错标都会暴露：

    · 换壳/改标 → 镭雕码与实际 MAC 不匹配；

    · 写入失败或错写 → 内部存储与镭雕码不匹配；

    · 扫 A 装 B → App 扫码得到的 MAC 与设备上报 MAC 不匹配。

    三道校验成本极低（都是软件比对），但能堵住产品全生命周期的身份类事故。建议写入后内部存储区设为只读。

#### 11.3.4 节拍重算

| # | 位置录入方式 | 录入耗时 | 单点位节拍 | 400 点位所需工时 | 

| A | 位置记忆 + 序号自动递增 | 约 10 s | 约 57 s | 6.3 h（可行） | 

| B | 每次完整选四级位置 | 约 25 s | 约 72 s | 8.0 h（实际约 325 点位） | 

| C | 现场只扫码，位置事后补录 | 约 6 s | 约 53 s | 5.9 h，但有时序错配风险 | 

方案 A 动作拆解（57 s）：移动定位 15 s + 撕膜贴附 10 s + 压合 6 s + 拨开关 4 s + 扫镭雕码 5 s + 位置确认 5 s + 姿态选择 4 s + 转场 8 s。

    400 点位/人日成立的前提是 App 必须实现"位置记忆 + 点位号自动递增"。若每次从头选四级位置，单点位多 15 s，日产能降到约 325——400 指标就不成立。这两项软件工作量很小，但对交付速度影响是决定性的，建议列为 App 的 P0，与固件同步开发。

#### 11.4 白名单机制

| 环节 | 动作 | 失败处理 | 

| 绑定提交 | 扫镭雕码自动带入设备信息，叠加现场录入的四级位置与姿态，提交云端 | 重复绑定/位置冲突 → 拒绝并提示 |

#### 11.5 安装流程（顺序不可颠倒）

- 取件：按箱取件。

- 能量核查：检查超容电压；<3 V 则 USB 补电至 3.5 V 再装（<10 min，边充边检不影响速度）。

- 基材判定：对照 11.2；乳胶漆面做拉拔试验。

- 粘贴：酒精擦拭 → 干透 → 撕膜 → 压合 ≥10 s。

- 拨开关至通电：将底部单刀开关从 OFF 拨到 ON（指甲或小工具，力度 3–5 N）。必须先通电再扫码——设备通电才能入网，扫码登记时才能即时校验在线状态。

- 扫码绑定：扫镭雕码（自动带出型号/MAC/批次）→ App 录入位置（默认沿用上次+序号递增）→ 选姿态与倾角 → 提交。

- 白名单校验：等待云端返回；未通过现场处理。

- 入网确认：App 显示上线即完成。

- 分批自检：2 h 后平台出报告与返工清单（含照度评估与策略核对）。

    现场自纠正机制：若安装工忘记拨 ON，设备不通电、扫码后无法入网，App 会提示"设备未上线"。文案中必须明确写"请确认底部开关已拨至 ON"，把提示变成纠正动作。

#### 15.2 术语

| 术语 | 说明 | 

| 有效触发角 | PIR 能可靠触发"有人进入"的水平角度（120°），即产品对外承诺的探测角 | 

| 有效保持角 | 人已进入有人态后，雷达能继续维持"有人"的角度（150°）；外环不可触发 | 

| T_radar_delay | 雷达延迟确认时间：从最后一次 PIR 触发开始计时，到期才启动雷达；PIR 每次触发即重置 | 

| T_scan | 雷达单次扫描时长，≤5 s，典型 2 s | 

| W_verify | 校验窗口，必须 ≥ T_scan | 

| PIR 门控 | 雷达仅在 PIR 触发后才启动，无人态完全断电 | 

| 乐观翻转 + 校验回滚 | PIR 触发即翻转并上报，雷达校验失败则回滚并报 E112 | 

| 进入回滚（E112） | 通俗说即设备"改口"：先说有人（灯亮），雷达发现没人，再撤销 | 

| 设备心跳（E102） | 设备存活 + 存在状态的周期上报，用于区分"无人"与"失联" | 

| 上报方式 I/A/H/L | 即时 / 聚合 / 随心跳 / 仅本地 | 

| 四层配置仲裁 | 能量底线 > 安全硬约束 > 云端基线 > 本地配置（需人工确认） | 

| 运输模式 | 开关 OFF 状态：系统断电、超容保留；待机约 2.3 µA | 

| 三重一致性校验 | 镭雕码 / 内部存储 / 实际 MAC 三者逐字段比对 | 

| 扫 A 装 B | 扫了 A 的码却装了 B 设备，靠"镭雕 MAC = 上报 MAC"拦截 | 

| 形态 A / 形态 B | 微能量供能 / USB 长期供电 | 

    核心结论：本产品的所有设计取舍都指向同一组矛盾——要快、要省、要不漏，三者在单一通道上无法同时满足。

    ① 拆通道是这套架构的根。开灯必须 ≤300 ms，云端往返最短也是一个唤醒窗口；上报必须省电，所以不能每条都即时。把"动作"归本地广播、"不丢"归父节点 ACK、"可运营"归云端聚合，三个目标才能同时成立。这也解释了为什么"有人进入"可以配聚合上报却毫不影响体验。

    ② 雷达延迟确认是省电的核心。只要 PIR 还在触发，计时器就重置，雷达永不启动；人坐下不动满 60 s，雷达才出马确认一次。有人活跃态功耗接近无人态（12 µA vs 11 µA），日均约 12 µA，平衡照度约 48 lux。

    ③ 上报根本不是耗电大头。单次云端上报约 0.28 µAh、本地广播约 0.05 µAh，办公场景一天合计约 14 µAh，占预算 6%。真正吃电的是 PIR 常开（约 50%）与雷达扫描（约 25%），所以省电第一优先级永远是减少雷达扫描次数。

    最后三条边界必须写进投标文档与规格书：外环 60°–75° 不能作为设计覆盖使用；本产品不承诺在完全无人活动的封闭空间中长期检测人的存在；"免换电"只对办公与走廊类场景成立，地库请用 USB 形态。
