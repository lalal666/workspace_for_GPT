一、产品概述与双形态定位

一句话定义：撕开背胶一贴即用、不接线不换电、坐在工位不动也不会关灯的存在传感器；完全无光的位置插一根 USB 就能获得更强性能。

1.1 背景与要解决的问题

现有方案致命缺陷现场表现
纯 PIR 人体感应只对移动热源响应，静止即判无人办公位静坐 5 分钟灯就灭；被迫把延时调到 20–30 min，节能率回落到 30% 以下
纯 24G 雷达对金属摆动、管道、穿墙敏感；常驻工作耗电高卷帘门、管道、窗帘导致"无人常亮"；电池型产品几个月没电
市电/电池型存在传感器需布线或 1–2 年换电池改造布线成本高于设备本身；万级点位无法规模化运维

本产品解法：PIR 做门控与主发现通道，雷达只在 PIR 静默后才启动做"静止保持"确认；能量管理 IC 统一管理光伏 / 超容 / 电池三源；3M 胶贴与镭雕扫码解决施工速度；USB 作为第二形态覆盖完全无光场景。

3.2 供能路径拆解

三条路径的角色必须分清，否则会误判"开关断开后设备应该完全不工作"。

路径走向关键特性
主能量路径光伏 / 超容 / 电池 → 能量管理 IC（三源统一管理）→ SW1 单刀开关 → Buck-Boost → 系统三源由一个 IC 统一调度，输出单路；开关就切在这一路上
USB 充电路径USB → 锂超容（直充，不经 IC）现场补电与产线预充走这条，速度快、不受 IC 充电逻辑限制
USB 直供路径USB → Buck-Boost → 系统（绕过 SW1）运输模式（开关 OFF）下插 USB 设备仍能工作——产线可在已拨 OFF 状态完成身份写入与测试
USB 旁路这个设计很实用。如果 USB 也要经过开关，产线就得"拨 ON 写入 → 拨 OFF 包装"，多一道动作且容易漏拨。现在可以在"已进入运输模式"的状态下直接插 USB 完成写入、校验、测试，最后拔线包装——漏拨风险大幅降低。

3.4 覆盖角：触发角 120° 与保持角 150°

两个角度不是"重叠与不重叠"的关系，而是两种不同的职责：PIR 负责"发现人"（触发），雷达负责"记住人还在"（保持）。

区域（以安装点垂线为 0°）PIR 触发角
（全角 120°）		雷达保持角
（全角 150°）		实际能力
0°–60°（核心区）可触发可保持完整双鉴：能发现人，也能维持"有人"
60°–75°（外环区）不可触发可保持只能保持：若人先在内圈被发现、再走到外环，雷达能继续维持；若人只在外环且不动，永远不会被发现
>75°不可触发不可保持无能力
这样理解就顺了：
· PIR 120° = 有效触发角，它决定了"这个点位能发现多大范围的人"，是产品的对外承诺值；
· 雷达 150° = 有效保持角，它决定了"人被发现后能在多大范围内继续被维持"，是体验增强值；
· 外环 60°–75° 的价值在于：人从内圈走过、转身到侧后方时，灯不会因为"走出 PIR 视野"而误灭——这是雷达宽角带来的实际收益；
· 局限同样要讲清：如果有人在侧后方一直静止不动，PIR 从未触发，系统就不会知道他在。这不是缺陷，是 PIR 门控架构的必然取舍。

对外表述规范：规格书写"有效探测角 120°（触发）／维持角 150°（保持）"，不写"探测角 150°"。销售布点时按 120° 计算覆盖，外环作为容错余量而非设计余量。

七、事件定义与上报配置体系

本章是全文档的核心依据：54 条事件逐条给出定义（触发条件 + 含义），并把事件出口拆成三条独立通道——本地广播、父节点上行、云端上报——分别规定默认方式、周期与可禁用性。研发可直接按此实现，测试可直接按此验收。

7.1 六条设计原则

  1. 每条事件必须有可判定的触发条件。"有人离开"不是一个名字，而是一组明确条件：离开判决计数达标 + 连续 N_leave 次雷达判无目标。没有触发条件的事件等于没有定义。
  2. 三条出口必须分开定义，不能用一个"上报方式"字段笼统表达。"要多快送到灯"和"要多省送到云"是两个正交需求。用同一个字段同时表达，结果只能二选一——要么为了开灯快而全部即时上云（耗电），要么为了省电而让开灯变慢（体验崩）。拆成三条后，两者可以同时最优。
  3. 上报方式是设备行为，必须是有限枚举。设备是休眠终端，无法响应任意节奏。所有配置必须落在设备能执行的有限档位内。
  4. 三级硬约束不可被配置突破。① 能量底线 ② 安全合规类（防拆、滞留、双鉴失效必须即时且不可禁用）③ 数据完整性（缓存溢出、白名单失败、联动确认超时必须报）。
  5. 本地配置是受控变更，必须经云端人工确认。生效后进入"待确认"态，授权人员确认才固化基线；72 h 未确认告警，7 天自动回退。
  6. 聚合不是丢弃，是延迟。聚合类事件仍完整记录在本地缓存，周期到达打包上报；期间若发生更高优先级事件，打包一并提前发送。

7.2 三通道出口模型

一条事件从设备发出，可能走三条完全不同的路。三者的目的、时延、确认语义、失败处理都不一样，必须分别配置、分别监控。

通道标识目的典型时延确认语义失败处理
D1 本地广播LB立即让灯/执行器动作，不等网络、不等云≤300 ms（泛洪，≤4 跳）灯侧 ACK 经父节点回传，代表"指令已被灯收到"重播 2 次（间隔随机 20–50 ms 防碰撞）；3 次无确认 → 上报 E606
D2 父节点上行UL把事件交进网络，保证不丢1 个唤醒窗口内（100–500 ms 命中，最长 ≤5 min）父节点 ACK，代表"事件已进入父节点暂存队列"未 ACK 则本地保留、下次唤醒重传；父节点暂存溢出须回通知（见 4.4）
D3 云端上报CL可运营、可统计、可追溯I ≤1 s／A 15 min–24 h／H 300–1800 s／L 不上报父节点 ACK 即视为"设备侧完成投递"按 A 档缓存、补报；缓存溢出报 E508
最容易埋的误解：父节点 ACK ≠ 云端已收到。ACK 只证明事件进了父节点暂存队列，而父节点到 CCO 是多跳，暂存溢出还会丢。若把两者混为一谈，会出现"设备以为上报成功、云端一条没收到"的静默丢数据——而且设备侧日志完全正常，排查会耗掉大量时间。
处置：每条事件带递增 evtSeq；云端按设备维度做序号连续性校验，发现空号即判丢事件并下发补报请求。这一条应写进通信协议，属于必做项而非优化项。

7.3 本地广播与灯侧确认

为什么本地必须单独占一条通道：云端往返最短也是一个唤醒窗口（秒级），而开灯要求 ≤300 ms 用户可感知。两者差一个数量级，不可能用同一条路满足。

要素设计
承载方式2.4G 泛洪组播，TTL ≤4 跳；携带群组 ID（32 个 group-ID 槽位）、动作码、evtSeq、需确认标志
时延预算组帧 ≤30 ms + 空口 ≤15 ms/跳 + 灯侧处理 ≤50 ms → 典型单跳 ≤120 ms，4 跳 ≤300 ms
确认机制灯侧回短 ACK 帧（不含业务载荷），由父节点汇聚后回传给本设备（这正是"由父节点确认灯是否收到"的落地方式）；超时 T_ack 默认 200 ms
重播策略超时未确认 → 重播，最多 2 次，间隔随机 20–50 ms（打散碰撞）；3 次仍无确认 → 上报 E606
去重灯侧按 evtSeq 去重，避免重播导致重复动作或重复计时
空口代价单次约 35 ms 占空（发 15 ms + 收窗 20 ms）。按 60 次/日计，占用可忽略；但密集部署仍须限制 TTL 与群组规模（≤8 台/父节点）
E606 与 E605 的分工要说清，否则现场会误判：
· E606 联动确认超时：灯没回 ACK → 指令没送到、或灯离线、或群组 ID 配错 → 查通信。
· E605 照明回路疑似故障：灯回了 ACK 但照度没升 → 指令到了、灯没亮 → 查灯具/驱动。
两者同时出现时优先查通信——因为通信不通时 E605 的判定本身也不可信。这个判断逻辑放在云端做，设备端不做。

最容易出的运维事故：低电时配置"看着生效、实际被强制改写"。举例：云端把 E102 配成"聚合 15 min"，但设备在 L4 档 P2 已停发。若设备不回执实际执行档，运维会以为"配了 15 min 为什么没数据"。
因此每次下发必须在回执中同时返回"配置值"与"当前实际执行值"，不一致时置告警标记。这条要写进 setReportPolicy 出参定义。

三重一致性校验的价值：镭雕码（物理铭牌）、内部存储（产线写入）、实际 MAC（芯片固有）三者必须一致。任一层被篡改或错标都会暴露：
· 换壳/改标 → 镭雕码与实际 MAC 不匹配；
· 写入失败或错写 → 内部存储与镭雕码不匹配；
· 扫 A 装 B → App 扫码得到的 MAC 与设备上报 MAC 不匹配。
三道校验成本极低（都是软件比对），但能堵住产品全生命周期的身份类事故。建议写入后内部存储区设为只读。

11.5 安装流程（顺序不可颠倒）

  1. 取件：按箱取件。
  2. 能量核查：检查超容电压；<3 V 则 USB 补电至 3.5 V 再装（<10 min，边充边检不影响速度）。
  3. 基材判定：对照 11.2；乳胶漆面做拉拔试验。
  4. 粘贴：酒精擦拭 → 干透 → 撕膜 → 压合 ≥10 s。
  5. 拨开关至通电：将底部单刀开关从 OFF 拨到 ON（指甲或小工具，力度 3–5 N）。必须先通电再扫码——设备通电才能入网，扫码登记时才能即时校验在线状态。
  6. 扫码绑定：扫镭雕码（自动带出型号/MAC/批次）→ App 录入位置（默认沿用上次+序号递增）→ 选姿态与倾角 → 提交。
  7. 白名单校验：等待云端返回；未通过现场处理。
  8. 入网确认：App 显示上线即完成。
  9. 分批自检：2 h 后平台出报告与返工清单（含照度评估与策略核对）。
现场自纠正机制：若安装工忘记拨 ON，设备不通电、扫码后无法入网，App 会提示"设备未上线"。文案中必须明确写"请确认底部开关已拨至 ON"，把提示变成纠正动作。

核心结论：本产品的所有设计取舍都指向同一组矛盾——要快、要省、要不漏，三者在单一通道上无法同时满足。

① 拆通道是这套架构的根。开灯必须 ≤300 ms，云端往返最短也是一个唤醒窗口；上报必须省电，所以不能每条都即时。把"动作"归本地广播、"不丢"归父节点 ACK、"可运营"归云端聚合，三个目标才能同时成立。这也解释了为什么"有人进入"可以配聚合上报却毫不影响体验。

② 雷达延迟确认是省电的核心。只要 PIR 还在触发，计时器就重置，雷达永不启动；人坐下不动满 60 s，雷达才出马确认一次。有人活跃态功耗接近无人态（12 µA vs 11 µA），日均约 12 µA，平衡照度约 48 lux。

③ 上报根本不是耗电大头。单次云端上报约 0.28 µAh、本地广播约 0.05 µAh，办公场景一天合计约 14 µAh，占预算 6%。真正吃电的是 PIR 常开（约 50%）与雷达扫描（约 25%），所以省电第一优先级永远是减少雷达扫描次数。

最后三条边界必须写进投标文档与规格书：外环 60°–75° 不能作为设计覆盖使用；本产品不承诺在完全无人活动的封闭空间中长期检测人的存在；"免换电"只对办公与走廊类场景成立，地库请用 USB 形态。
