### 1.4 需求基线

#### 1.4.1 硬件基线

- 主控：TLSR8258F512ET32，24 MHz 32 bit，Flash 512 KB / SRAM 64 KB，1.8～3.6 V，-40～+85 ℃，集成 BLE。
- 传感：PIR（触发角 120°）、24 GHz 雷达（保持角 ≥150°，带 DRDY）、照度、温湿度。
- 供电：OPV + 20 F 超容为主，CR2450 600 mAh 备用，USB Type-C 5 V 可长期外供。
- 接口：USB Type-C 6 pin（充电 + 直供 + 产测写入）。
- 天线：板载。结构：主板 + 光照/温湿度小板分体。
- 防拆：支架侧检测器件（方案见 4.12，待硬件签核）。

#### 1.4.2 软件基线

| 项                 | 基线                                         |
| ----------------- | ------------------------------------------ |
| BSP：SDK / BLE 协议栈 | 待 FW 签核（要求支持 BLE 链路层加密、连接参数协商、广播扩展）        |
| 应用层               | 应用层运行在BSP之上，需具备功能模块解耦，功能功能模块可复用。           |
| 云与端协议             | 沿用 V1.5 网关协议（MQTT over TLS + JSON），新增逐事件接口 |
| 小程序               | 「澜潮智联」，需支持扫码组网、选点勘测、近场调试三套流程               |
#### 1.4.3 结构基线

三层结构：A 面 PC 铭牌盖板（防水胶，OPV 与照度开窗去胶、温湿度微针点阵打孔）；中框 ABS+PC 预留卡扣凹槽；背板 ABS+PC 卡扣安装。整机无开孔、无麦克风孔、无可见螺钉。



**口径冲突处理原则**：能量与器件参数以 BOM 实装为准；性能指标以"可测工况 + 实测"为准；凡是写"建议/候选/待验证"的数值，一律不得对外承诺。

## 02 产品概述

### 2.1 背景与痛点

| 现有方案        | 致命缺陷                | 现场表现                                         |
| ----------- | ------------------- | -------------------------------------------- |
| 纯 PIR 人体感应  | 只对移动热源响应，人一静止就判无人   | 工位静坐 5 分钟灯就灭；只好把延时调到 20～30 min，节能率回落到 30% 以下 |
| 纯 24G 雷达    | 对金属摆动、管道、穿墙敏感，常开耗电高 | 卷帘门、窗帘导致"无人常亮"；电池型产品几个月就没电                   |
| 市电/电池型存在传感器 | 要布线，或 1～2 年换电池      | 改造布线成本高于设备本身；万级点位无法规模化运维                     |

上一代多合一传感器把 PIR、雷达、光照、红外发射塞进一台，功能互相牵制。本版按场景拆成 SKU，本文只定义 **SKU2 双鉴存在传感器**：只做"人在不在 + 有多亮"，把"控什么"交给生态设备。

### 2.2 产品定位

面向室内空间的**低功耗人体存在感知与生态联动传感器**：自己不接市电、不布线，靠室内光和备用电池活着；发现人之后，把结论交给同组的灯和空调去做动作。

### 2.3 产品定义与三种供能形态

双鉴存在传感器集成 PIR、24 GHz 毫米波雷达、照度检测与 BLE 通信，采用 OPV + 超容主供、CR2450 兜底，同时支持 USB 常供电。

| 形态       | 供能方式                  | 适用场景                     | 能力差异                         |
| -------- | --------------------- | ------------------------ | ---------------------------- |
| A 微能量    | OPV + 20 F 超容，电池兜底    | 办公、走廊、会议室、卫生间等有有效受光时长的点位 | 标准性能：雷达延迟确认 60 s 起，受能量分级约束   |
| B 备用电池   | CR2450 自动切入（超容低于切入门槛） | 连续阴天、短时断光的兜底             | 维持基本检测与心跳，续航按 5.9 核算         |
| C USB 外供 | 5 V 直供 + 给超容补能        | 地库、无窗库房、机房等长期低照度点位       | 高性能模式：雷达延迟可缩至 15～30 s，不因低电降级 |

### 2.4 产品特点

- **双鉴而不是双传感器**：PIR 门控雷达，雷达只在 PIR 静默后才出马，既省电又不误判静止。
- **两条联动路径**：本地 BLE 直达（灯 300 ms 内亮）与云端策略下发，断网时本地照常工作。
- **会算电的设备**：自建 LPNMS 能源模型，预测还能撑多久，撑不住时按既定顺序牺牲功能，而不是随机死机。
- **装得快**：背胶 + 万向支架随手贴；扫机身码录入位置；选点阶段就用设备自己的照度数据判定点位好坏。
- **拿走会喊**：设备离开支架触发防拆告警，硬件级检测，不依赖软件推断。

### 2.5 范围

**本产品做（In Scope）**

- PIR 门控 + 24G 延迟确认的双鉴存在检测，输出"有人/无人/未知"三态。
- 微能量、备用电池、USB 三种供能自动切换与能源管理。
- 照度四用途：联动判断、安装选点与质检、白天免开灯、灯具故障辅助判断。
- 事件生成、三通道上报、断链缓存补报、逐事件可配置。
- BLE 组网两条路径（LPN 自动组网 / 扫码 + 云下发）、入网鉴权、链路加密与防重放。
- 心跳、时间同步与时间戳、OTA 升级、云端超管运维、近场 BLE 维护。
- 生态联动策略：同组灯具、空调控制器。
- 防拆检测与告警（硬件支持）。

**本产品不做（Out of Scope）**

- 不上传雷达原始中频数据。
- 雷达不作为独立触发源，只由 PIR 唤醒后启动。
- 不做中继/路由（`canRelay=false`）；不做 PLC、不做 Sub-G；不做独立网关。
- 不做多人计数、距离分档（转预留版本）。
- 不做室外、雨淋、凝露环境；不做粗糙易脱落基材。
- 不做红外发射控制空调（该能力归 SKU3）。

**为什么 USB 要旁路开关**：

1、产线可在"已拨 OFF（运输模式）"的状态下插 USB 完成身份写入、校验和测试，最后拔线包装，避免"写入后再拨 OFF"的漏拨风险。（type-C 6 pin能否支持数据传输带核签）

2、即使超容出现概率性损坏，此节点也可用作USB供电在别的地方使用。

| -- | ---------- | ---------- | -------------- | ------------ | ---- |
| L1 | ≥3.35 V    | 30 s       | 300 s / 15 min | 按配置          | 100% |

| L4 | 2.7–3.0 V  | 180 s（待实测） | 900 s / 24 h   | 停 P2，仅 P0/P1 | 50%  |
| L5 | <2.7 V     | 300 s      | 1800 s / 24 h  | 仅 P0         | 25%  |

**低电必须同步做的两件事**：把 `N_leave` 加大（L4 取 5、L5 取 6），否则会出现"电量越低越容易误关灯"的反常体验；把"实际执行值"随回执上报，否则运维会以为"配了 15 min 为什么没数据"。

#### 4.1.3 牺牲顺序与禁止项

能量不够时不是"随便关点东西"，而是按固定顺序退让：

| 顺序  | 牺牲什么           | 理由                |
| --- | -------------- | ----------------- |
| ①   | P2 类事件的聚合上报    | 只影响报表及时性          |
| ②   | 雷达复查频次（拉长间隔）   | 影响静止分辨率，但不丢"有人"核查 |
| ③   | 发射功率           | 影响链路余量，可被重传补偿     |
| ④   | 停发 P2，仅保 P0/P1 | 保留业务主干            |
| ⑤   | 受控保电（停测）       | 最后手段，须场景允许        |
**禁止项（不得因省电而做）**

- 不得停止 PIR 值守（PIR 是唯一 24h 的发现通道）。
- 不得因低电、停测、无数据而直接判定"无人"，只能记"未知"。
- 不得关闭安全类与完整性类事件（防拆、双鉴失效、超容欠压、缓存溢出等）。
- 不得静默丢事件而不计数。

#### 4.1.5 能量预算（参考值，实测签核）

| 耗能项              | 无人态           | 有人·活跃         | 有人·静止          |
| ---------------- | ------------- | ------------- | -------------- |
| PIR 常开           | 2～5 µA        | 2～5 µA        | 2～5 µA         |
| 24G 雷达           | 0             | 0（计时器不断重置）    | 约 5 µA         |
| MCU 休眠           | 1～3 µA        | 1～3 µA        | 1～3 µA         |
| 上报折算             | 0.3 µA        | 0.8 µA        | 0.8 µA         |
| 超容漏电             | 2 µA          | 2 µA          | 2 µA           |
| 管理 IC + DC-DC 静态 | 2.3 µA        | 2.3 µA        | 2.3 µA         |
| 照度通道             | <0.5 µA       | <0.5 µA       | <0.5 µA        |
| **合计**           | **约 8～11 µA** | **约 9～12 µA** | **约 14～17 µA** |

**结论**：真正吃电的是 PIR 常开（约 50%）与雷达扫描（约 25%），上报只占个位数。所以省电的第一优先级永远是"减少雷达启动次数"，而不是压缩上报。

### 4.2 通信与安全（FR-2xx）

**要点**：同一条事件要同时满足"快、不丢、可运营"三个互相矛盾的目标。解法不是把一条路做快，而是拆成三条路。

#### 4.2.1 三通道出口模型

```mermaid
    E --> D3("D3 云端上报<br/>I / A / H / L")

    D2 --> P("父节点")
```

| 通道       | 目的          | 典型时延                                   | 确认语义             | 失败处理                               |
| -------- | ----------- | -------------------------------------- | ---------------- | ---------------------------------- |
| D1 本地广播  | 让灯立刻动，不等网络  | ≤300 ms（4 跳内）                          | 执行端短 ACK = 指令已收到 | 重播 2 次（间隔随机 20～50 ms）；3 次无确认报 E606 |
| D2 父节点上行 | 把事件交进网络，不丢  | 1 个唤醒窗口内                               | 父节点 ACK = 已进暂存队列 | 未 ACK 则本地保留，下次唤醒重传                 |
| D3 云端上报  | 可统计、可追溯、可配置 | I ≤1 s / A 15 min～24 h / H 随心跳 / L 不上报 | 设备侧投递完成          | 按档缓存补报；溢出报 E508                    |

#### 4.2.2 BLE 链路安全

本机的链路全部是 BLE，安全必须按 BLE 的实际能力分层设计，不能假设"有加密就安全"。

| 层    | 措施                                           | 说明                    |
| ---- | -------------------------------------------- | --------------------- |
| 身份   | 一机一密：出厂注入设备专属密钥/证书，机身码与密钥绑定                  | 扫码照片、相同 MAC 都不能单独通过鉴权 |
| 配对   | 连接链路启用 BLE Secure Connections 配对与绑定，密钥存于受保护区 | 未配对设备不得读写配置           |
| 链路保护 | 已配对连接使用协议栈 AES-CCM 加密；应用层再做一层认证加密            | 防中间人、防篡改              |
| 广播保护 | 无连接的本地广播本身不加密，业务payload载荷由固件先加密并附校验后再发出      | 接收端校验不通过直接丢弃          |
| 防重放  | 受保护的会话序号/计数器 + 绑定代次 + 时间戳窗口；重启、换父、换绑后旧包失效    | 一条指令只生效一次             |
| 密钥管理 | 按设备 / 项目 / 组 / 用途隔离；支持轮换、失效、版本切换             | 普通日志禁止出现密钥与配网凭据       |
| ID     | 需求描述                                                    | 优先级 | 验收口径                    |
| ------ | ------------------------------------------------------- | --- | ----------------------- |
| FR-207 | 设备↔父节点、设备↔执行端、近场维护三条链路均须提供机密性、来源认证与完整性校验；校验失败即拒绝并保持原状态。 | P0  | 逐段抓包：未授权方读不出业务内容；篡改报文被拒 |
| FR-208 | 拒绝明文降级：加密协商失败不得回退到明文传输。                                 | P0  | 强制协商失败，连接被断开而非降级        |
| FR-209 | 接收端校验发送者、授权组、时效凭据后才执行；旧包、重复包不得开关灯、续计时、改配置或新增记录。         | P0  | 重放 100 次历史帧，动作次数为 0     |
| FR-210 | 近场维护会话独立鉴权、独立权限、限时有效（≤30 min），到期自动退出并恢复原策略。             | P0  | 超时后连接被拒；退出后策略回读一致       |
| FR-211 | 调试口与产测接口量产关闭；日志、事件、上报报文均不含密钥与凭据。                        | P0  | 出厂固件扫描 + 日志抽样检查         |

#### 4.2.3 报文与字段约定

| 字段        | 用途            | 约束                                                 |
| --------- | ------------- | -------------------------------------------------- |
| `eventId` | 上行事件唯一标识      | 重传/补报/换父不变；云端按此去重                                  |
| `evtSeq`  | 灯侧联动去重序号      | 单调递增，按设备维度校验连续性                                    |
| `ts`      | 事件发生时间（设备本地秒） | 与 `bootId` 组合，用于还原 UTC                             |
| `bootId`  | 本次开机标识        | 跨重启排序与回填的边界                                        |
| `tsConf`  | 时间可信度         | `valid` 有效已同步/ `restored`曾经同步但基准已失效 / `unknown`未同步 |
| `actId`   | 动作指令 ID       | 同一动作多目标投递时用于核对重复                                   |
**注意**
1、bootId:事件只在同一个 BootID 内部做时序排序、断链补报回填；一旦设备重启、`bootId` 变了，旧批次事件`eventId`、和新批次事件不能混排、不能跨 `bootId` 回填。**排序边界**：网关 / 云端做事件时序排序时，**只在相同 `bootId` 里面按 `evtSeq` 排先后**；
不同 BootID 的事件，不能单纯靠 evtSeq 对比先后。**回填边界**：断网缓存、环形缓存里存的历史事件，**只允许在当前 BootID 有效期间向上回填补报**；
设备一旦重启，BootID 更新，上一轮 BootID 里没发完的旧事件直接丢弃。

### 4.3 BLE 组网与鉴权（FR-3xx）

**要点**：两条入网路径，一套鉴权标准。路径决定"谁发起"，鉴权决定"能不能进"。

#### 4.3.1 两条组网路径


### 4.4 事件机制（FR-4xx）

**要点**：一条没有明确触发条件的事件等于没有定义。所以每条事件必须写清"什么时候产生、发给谁、要不要确认、丢了怎么办"。

#### 4.4.1 事件生成原则

- **可判定**：触发条件必须是可测的状态或计数，例如"连续 N_leave 次有效空判 + 等满 T_leave"，而不是"人好像走了"。
- **可追溯**：记录源设备、类型、`eventId`、发生时间、测量值与原因；转发时保留原始来源与发生时间。
- **三态**：人员状态只有"有人 / 无人 / 未知"，数据不足时必须记"未知"，不得默认"无人"。
- **单次生效**：状态变化只记一次；持续维持同一状态时更新快照或做周期统计，不重复产生事件。

#### 4.4.2 事件分类

| 编号段  | 类别      | 典型事件                                          | 是否可禁用    |
| ---- | ------- | --------------------------------------------- | -------- |
| E1xx | 存在检测    | 有人进入、有人离开、微动存在、活动升级、滞留超时、进入回滚                 | 主干不可禁用   |
| E2xx | 双鉴融合与降级 | 双鉴一致确认、双鉴冲突、雷达降级、PIR 故障、双鉴失效、通道恢复             | 故障类不可禁用  |
| E3xx | 能源与电源   | 采能恢复、能量不足、能量临界、临终上报、上电启动、超容欠压、电池低电            | 底线类不可禁用  |
| E4xx | 自检与安防   | 周期自检、雷达自检失败、PIR 自检失败、**防拆/脱落**、探测窗遮挡          | 安防类不可禁用  |
| E5xx | 生命周期与运维 | 上线、链路恢复补报、入网完成、配置生效/拒绝、OTA 状态、时钟偏差、缓存溢出、白名单失败 | 完整性类不可禁用 |
| E6xx | 光照与联动   | 照度阈值穿越、联动执行反馈、群组联动触发、免开灯生效、照明回路疑似故障、联动确认超时    | 多数可禁用    |


**滞留超时**：场景：已经判定【有人】，开始计时，在设定滞留时长内，雷达 / PIR 再也没有捕捉到人体（静止、微动都没检测到），计时器跑满 → 触发\
**滞留超时事件**，状态切为无人。作用：就是照明联动里的 “保持延时”，防止人静止不动直接误判无人、灯秒关。
**进入回滚**：PIR 触发了，但是雷达核验不通过，撤销这次有人判定。\
**雷达降级**：雷达异常 / 供电不足时，退出双鉴，仅依靠 PIR 做存在检测，同时上报降级事件。\
**白名单失败**：设备入网鉴权时，设备 ID 不在平台 / 父节点点位白名单内，入网校验失败。\
**照度阈值跨越**：照度值单向跨过设定阈值（由暗到亮 / 由亮到暗），触发一次判定。\
**照度阈值穿越**：照度来回在阈值附近抖动，多次穿过阈值。\
**联动执行反馈**：被控灯具收到指令后回传是否执行成功的应答。\
**群组联动触发**：本传感器状态满足条件，向组内所有设备下发联动指令。\
**免开灯生效**：照度高于免开灯阈值，有人时不触发开灯联动。\
**照明回路疑似故障**：下发开灯指令后，未收到灯具正常应答，判定回路异常。\
**联动确认超时**：发出联动指令后，在规定窗口内没有收到被控设备应答。\

### 4.8 运维与云端超管（FR-8xx）

**要点**：后期规划中设备支持装在天花板上，人上不去。所以平台必须能在设备在线时"远程动手"，但这类能力等价于 root 权限，必须带闸门。

### 4.10 PIR + 24G 双鉴策略（FR-10xx）

**要点**：PIR 负责"发现人"，雷达负责"人还在不在"。用延迟确认把两者串起来，就能同时做到"有人时省电"和"静止不误判"。

#### 4.10.1 三个时间参数

| 参数 | 取值 | 定义与硬约束 |
| --- | --- | --- |
| T_scan | ≤5 s，典型 2 s | 雷达从上电到输出首个有效结果；由模组实测标定写入固件（只读） |
| T_radar_delay | 15 / 30 / 60 / 120 / 180 / 300 s | 有人态下从最后一次 PIR 触发开始计时，到期才启动雷达；PIR 每次触发即重置 |
| W_verify | 默认 T_scan + 1 s | 硬约束：W_verify ≥ T_scan，否则会出现"没等结果就回滚" |

#### 4.10.2 门控状态机

```mermaid
stateDiagram-v2
    [*] --> S0
    state "S0 无人 · PIR 值守" as S0
    state "S1 疑似有人" as S1
    state "S2 有人 · 计时中" as S2
    state "S3 雷达确认" as S3
    state "S4 离开判决" as S4
    state "回滚 E112" as RB

    S0 --> S1: PIR 触发
    S1 --> S2: 雷达检出（AND 成立）
    S1 --> RB: 雷达有效否定
    RB --> S0: 雷达断电
    S2 --> S2: PIR 再次触发（重置计时）
    S2 --> S3: 静默满 T_radar_delay
    S3 --> S2: 检出 → 重置计时
    S3 --> S4: 未检出 → 计数 +1
    S4 --> S2: 期间检出 → 清零
    S4 --> S0: N_leave 达标 + 等满 T_leave
```

#### 4.10.3 三段式逻辑

| 阶段 | 触发与通道 | 判决 | 设计意图 |
| --- | --- | --- | --- |
| 无人 → 疑似有人 | 仅 PIR 可触发 | PIR 触发立即置"疑似有人"并上报（≤300 ms），同时给雷达上电校验 | 开灯速度由 PIR 保证；进入阶段必须立刻校验，否则灯会白亮很久 |
| 疑似有人 → 确定有人 | AND 校验 | 雷达在 W_verify 内检出 → 确认；有效否定 → 回滚并报 E112；超时/无有效样本 → 未知 | 用事后校验滤掉 PIR 误触发（阳光、热源、气流） |
| 有人 → 有人（保持） | PIR 重置 + 到期复查 | PIR 任一触发重置计时器，雷达不启动；到期才扫一次 | 这是省电核心：PIR 活跃时雷达零启动 |
| 有人 → 无人（离开） | 仅雷达 + 多次判决 | 连续 N_leave 次有效空判 + 等满 T_leave 才翻转，单次不翻转，PIR 不参与 | 关灯不可逆，必须最保守 |

**三个必须承认的边界**（写进规格书与投标文档）：

1. 外环 60°～75° 只能保持、不能触发；布点按 120° 计算，外环只作容错余量。
2. 不承诺"在完全无人活动的封闭空间中长期检测人的存在"；这类场景应改用常供电 + 常开雷达方案。
3. 极限静止（判离后完全不动且 PIR 无触发）存在盲区，靠 N_leave、T_leave、布点冗余与场景明示共同收敛。

| 微动灵敏度 | 可检出 ≤0.05 m/s | 静止漏报指标无法达标 |

### 4.12 防拆：设备被从支架带走（FR-12xx）

**要点**：这是本机唯一带"物理对抗"性质的需求。软件推断不可靠，必须硬件给信号；而硬件信号又会误报，所以要做双条件确认。

#### 4.12.1 硬件方案对比

| 方案 | 原理 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| 霍尔 + 支架磁铁 | 设备离开支架 → 磁场消失 | 无接触、无磨损、成本低、易做在位检测 | 强磁干扰可能误判 | **推荐主方案** |
| 机械微动/顶针开关 | 支架压住顶针，离开即断开 | 判定最直接 | 顶针易氧化、装配公差敏感、长期压缩疲劳 | 备选 |
| 加速度计（G-sensor） | 检测搬动、跌落、姿态突变 | 可区分"被拿走"与"被碰一下" | 常开耗电，与微能量冲突 | 作为辅助确认，间歇采样 |
| 离墙检测（电容/光电） | 检测与安装面距离 | 覆盖"连支架一起拔走" | 受基材影响大，标定复杂 | 预留 |

**推荐组合**：霍尔为主判据（在位/离位），加速度计间歇采样作辅助确认（区分"拿走"与"轻微碰动"）。两者同时成立才判定为"被带走"，避免打扫卫生时误报。

本机没有开关电源，但有两处强干扰源：**24 GHz 雷达本振**与**BLE 射频**；同时 USB 供电会把外部噪声引进来。EMC 必须按"发射"和"抗扰"两侧分别验收。
